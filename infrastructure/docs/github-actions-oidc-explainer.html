AWS infrastructure CI

GitHub Actions OIDC, reusable workflows, and the AWS plan role

This page explains why the PR plan role needs a narrow trust policy, what reusable workflows add, and how this applies to .github/workflows/aws-infrastructure.yml.

The short version

GitHub Actions uses OIDC to ask AWS for temporary credentials. AWS decides whether to issue those credentials by checking claims in the GitHub-issued token. Our plan role currently trusts pull request jobs from this repository. That is useful, but broad: any future PR workflow with id-token: write could try to assume the same role.

Recommended for this PR: add more trust-policy conditions, such as repository and workflow, so the plan role is limited to the AWS infrastructure workflow.

How OIDC works in this repo

Pull requestchanges AWS workload code
GitHub jobhas id-token: write
OIDC tokencontains claims
AWS trust policychecks claims
Plan roleruns tofu plan

The token includes facts such as the repository, event type, workflow name, branch or pull request context, and audience. AWS role trust policies compare those facts before allowing sts:AssumeRoleWithWebIdentity.

The risk in the current plan-role trust

The plan role was intentionally separated from the apply role:

Pull request workflow  → jellylabs-tofu-plan → tofu plan
Push to main           → jellylabs-tofu-main → tofu apply

The weak point is this trust condition:

token.actions.githubusercontent.com:sub = repo:chris-jelly/jellylabs-dsc:pull_request

That means “a pull request workflow in this repo.” It does not mean “the AWS infrastructure workflow.” If another PR workflow later gets id-token: write, AWS may let that job assume the plan role too.

Normal workflows versus reusable workflows

Concept What it means Why it matters for OIDC
Normal workflow A workflow file triggered directly by events like pull_request or push. Good for this repo today. AWS can check claims like repository, sub, and workflow.
Reusable workflow A workflow called by another workflow with jobs.<id>.uses. Enables stronger “approved workflow” patterns through job_workflow_ref.
id-token: write A workflow permission that lets a job request a GitHub OIDC token. It does not grant AWS access by itself. AWS still decides based on the role trust policy.

What the reusable-workflow article adds

The article describes a stronger pattern: put cloud login inside an approved reusable workflow, then make the cloud provider trust only that reusable workflow. GitHub exposes the called workflow path in the job_workflow_ref claim. 

caller workflow
  uses: org/repo/.github/workflows/approved-plan.yml@v1

OIDC claim
  job_workflow_ref = org/repo/.github/workflows/approved-plan.yml@refs/tags/v1

This pattern is useful when many repositories or workflows should use one approved deployment path. It is more structure than we need right now, but it is a good future option.

How we should apply this now

Near-term fix

  • Keep the current normal workflow.
  • Keep sub = repo:...:pull_request.
  • Add repository = chris-jelly/jellylabs-dsc.
  • Add workflow = aws-infrastructure.

Why this is enough for now

  • It blocks other differently named PR workflows from using the plan role.
  • It keeps the PR small.
  • It avoids repo-level OIDC subject customization.

Future hardening

  • Move cloud-authenticated steps into a reusable workflow.
  • Constrain AWS trust with job_workflow_ref.
  • Optionally customize GitHub's sub claim if direct claims are not enough.
Caveat: workflow identifies the workflow name, not the file path. A reusable workflow plus job_workflow_ref gives a stronger path-based control, but requires a larger workflow design change.

Proposed trust-policy direction

The plan role should require all of these claims:

aud        = sts.amazonaws.com
sub        = repo:chris-jelly/jellylabs-dsc:pull_request
repository = chris-jelly/jellylabs-dsc
workflow   = aws-infrastructure

That narrows the role from “any pull request workflow in this repo” to “the AWS infrastructure pull request workflow in this repo.” If the workflow architecture grows, revisit the reusable-workflow pattern.
